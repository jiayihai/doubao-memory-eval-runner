# 构建思路与关键取舍

## 问题

长期记忆测评需要跨多条消息和多个会话输入历史，再检查产品是否召回。人工执行容易漏发、错会话或丢失回复，因此先把执行和证据保存做成固定流程。

## 演进过程

| 阶段 | 重点 |
| --- | --- |
| 收敛范围 | 先沿用54条旧B自动消息，聚焦豆包执行，暂缓评分和多产品。 |
| 选择路线 | 讨论现成工具和Power Automate桌面隔离，最终回到现有CDP主线，避免持续占用鼠标操作。 |
| 稳定与恢复 | 增加窗口、真实完成数、断点及继续按钮；分别核对发送确认、回复完成和测评间隔。 |
| 日志定位 | 针对后台停滞、页面加载和红色感叹号补观察与保护，不仅凭最小化或网络推断原因。命名失败曾定位到click与pointerdown事件行为差异。 |
| 逐条采集 | 单次读取页面只能得到已加载内容；改为执行中及时保存完整回复，按会话编号生成备份。 |
| 结果回填 | 先按钮生成副本，再接流程结束自动生成；不逐条实时写Excel，不改原模板。 |
| 通用输入 | 用全过程执行表＋独立问题表统一数据，先校验预览再接执行，换同格式文件不逐条改代码。 |
| 完成验收 | 原V1.6.0短表通过，完整表60条自动步骤完成，保留人工边界及双份结果。 |

## 作者的主要思考

- 方便恢复比追求绝不中断更实用；发送结果不明时不能为了继续而盲目重发。
- 等待用于模拟真实使用节奏，应从完整回复结束后计算，恢复不重新计时。
- 会话ID已存在时返回原会话；身份标签不能冒充真实账号隔离。
- 原文发送和问题映射使用固定字段、唯一ID，不让模型改写或猜匹配关系，避免为数据搬运额外调用LLM。
- 所有回答保存到全过程，问题回答另汇集到独立问题表，供后续按评分标准评判。
- 原模板与每轮结果分开；回填副本在原表目录和运行记录双份保存。
- 每次只接入一个阶段，作者实际验收后再继续，保护已稳定的功能。

需求、场景、优先级与验收由作者主导，代码实现和故障排查使用AI辅助。执行成功与测评通过是两件事；专用账号的对话/记忆清理、多产品与评分属于未来工作，未混入当前成果。
